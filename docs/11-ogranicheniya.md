# 11. Ограничения и заметки

Сводка известных проблем, осознанных ограничений и точек роста. Часть пунктов —
это сознательные решения (объяснение дано в KDoc), часть — технический долг.

## Технический долг

### Мёртвый код `task2.db` / `task2.presentation` / `task2.ui` / `task2.di`

`AppContainer`, `ChatViewModel`, `ChatScreen`, `ChatDatabase` **не создаются ни одной
точкой входа**: обе точки входа собирают `Task3Container`. Соответственно:

* файл `chat.db` в работающем приложении не создаётся;
* базовый экран чата недостижим из UI продукта;
* `ChatRepositoryImpl` и `RoomMemoryStore` — работающие классы без пользователей
  (`RoomMemoryStore` используется только в тестах и как пример реализации `MemoryStore`).

Это наследие переноса из челленджа, где недели шли последовательно. Удаление
указанных пакетов безопасно, **кроме** тех мест, где `task2` переиспользуется
(`ModelCatalog`, `Network`, `PromptBuilder`, `ChatMessage`, `EngineStatus`,
`LlamaBridge`, `GenParams`, `CHATML_TEMPLATE`, платформенные `actual`-функции).

Побочный эффект для разработчика: поиск «логики чата» даёт два независимых
реализации — `ChatRepositoryImpl` и `RagRepository`. Второй не наследует первый.

### Устаревшие ProGuard-правила

```proguard
-keep class task2.llama.JniLlamaBridge { *; }
-keep class task2.llama.** { *; }
```

Класс `JniLlamaBridge` в проекте отсутствует — это следы эпохи llama.cpp/JNI
(текущая реализация — `LiteRtLlamaBridge`, нативный код приходит из AAR).
Для релиза правила надо пересмотреть: нативные символы LiteRT-LM,
по всей видимости, тоже требуют `keep`.

### Дублирующиеся импорты в `ChatTab.kt`

`androidx.compose.foundation.layout.Column` и `…Row` импортированы дважды
(строки 4–5 и 14–15 в `shared/src/task3/ui/ChatTab.kt`). Компилируется без ошибок,
но признак небрежности.

### Мёртвая логика в `Task3ViewModel`

```kotlin
Triple(m.label, llmStatus !is EngineStatus.Error || true, "")
```

Выражение `x || true` всегда истинно, поэтому для скачанной локальной модели
`canChat` всегда `true` независимо от статуса движка. Задумывалось, по-видимому,
что отправка должна блокироваться при `EngineStatus.Error`.

### `combine` на 13 потоков с `@Suppress("UNCHECKED_CAST")`

`Task3ViewModel` объединяет 13 `StateFlow` через `combine` с массивом `args`
и приведением типов, затем распаковывает в `data class Partial`. Работает, но
небезопасно: добавление или перестановка потока требует синхронной правки
индексов в трёх местах. Альтернатива — отдельный `data class` для состояния
репозитория и `map`.

### Дублирование кода мостов android / jvm

`LiteRtLlamaBridge` для Android и для JVM — два почти идентичных файла
(125 и 108 строк), различаются лишь деталями. Сейчас это безопасно: обе платформы
подключают один и тот же `litertlm`, и `actual`-функции обязаны быть разделены.
Дублирование ушло бы в `expect`-общую часть при появлении реального различия
(например, специфичного desktop-бэкенда).

### Параметр `nCtx` игнорируется

`LlamaBridge.load(modelPath, nCtx = 2048, nThreads = 4)` принимает размер контекста,
и репозитории передают туда `AiModel.defaultCtx` (4096 или 1280), но **обе реализации
`LiteRtLlamaBridge` параметр не используют**: `EngineConfig` в LiteRT-LM не имеет
такого поля. Размер KV-кэша берётся из самого бандла — он закодирован в имени файла
(`…_ekv4096.litertlm`, `…_ekv1280.litertlm`). Практического эффекта нет, но параметр
вводит в заблуждение: создаётся впечатление, что размер окна настраивается из кода.
Либо прокинуть параметр в LiteRT-LM, если он там появится, либо убрать его из интерфейса.

### `AiModel.sha256` не используется

Поле объявлено (`val sha256: String = ""`), но ни разу не читается. Проверка целостности
сводится к сравнению размера файла — см. ниже.

## Осознанные ограничения

### Десктопные эмбеддинги — хеш-векторы

На JVM нет нативного `EmbeddingEngine`, поэтому `FakeEmbedBridge` считает
`hashingEmbed` (символьные триграммы в 768-мерный вектор). Последствия:

* UI индексации работает полностью, но **качество поиска на десктопе бессмысленно** —
  похожие тексты не будут находиться;
* `FakeEmbedBridge` живёт в `src@jvm`, то есть в основном коде, а не в тестах;
* десктоп пригоден для разработки UI и отладки, но не для оценки качества RAG.

### Полный перебор вместо ANN-индекса

`cosineTopK` сканирует все чанки. Для десятков статей Википедии это правильный
выбор (просто, предсказуемо, без зависимостей), но при тысячах документов
подсчёт станет заметным на телефоне. Тогда понадобится ANN-структура
(HNSW, IVF) — а это ещё одна зависимость и управление памятью.

### `MIN_SCORE = 0.55` — подобранная константа

Порог задан вручную и зависит от embedding-модели и корпуса. В коде прямо
написано, что его нужно «точить на 3-5 запросах». Смена модели эмбеддингов
почти наверняка потребует нового порога. Перспективный путь — калибровка
по распределению расстояний на валидационной выборке.

### Окно контекста фиксировано

10 сообщений в базовом чате и 6 в RAG — константы в `PromptBuilder` и
`RagRepository.answerLocal`. Длинные диалоги теряют нить, но это сознательный
размен в пользу размера KV-кэша маленьких моделей (1280–4096 токенов).

### Размер чанка фиксирован

`maxChars = 1000` подобран под `maxInputLength = 512` токенов у EmbeddingGemma.
Другая embedding-модель потребует пересчёта: слишком крупные чанки обрезаются
нативным кодом (и теряют хвост), слишком мелкие ухудшают качество поиска.

### Один источник документов

Только Википедия. `WikiLoader` — единственный загрузчик; добавление PDF/локальных
файлов потребует интерфейса `DocumentLoader` (сейчас его нет, `addWikiDoc`
работает только с Википедией поимённо).

### Один embedding-эндпоинт

В `EmbedCatalog` всего одна модель. `FakeEmbedBridge` всегда отдаёт `dim = 768` —
при добавлении моделей в каталог фолбэк начнёт врать о размерности.

### Модели не проверяются по хешу

`AiModel` содержит поле `sha256`, но оно **не используется**: сравнение хешей
1.5-гигабайтного файла на телефоне дорого. Проверка ограничена размером
(не меньше 80 % от ожидаемого). Битый, но полностью скачанный файл поймает
рантайм LiteRT-LM при загрузке — сообщение об ошибке будет техническим.

### Нет автоматического скачивания моделей

В RAG-режиме пользователь сам выбирает и скачивает модель. В базовом чате
`ChatViewModel` прогревал дефолтную модель в фоне — но этот путь в продукте
не используется.

### Скачивание без `resume`

`downloadFile` всегда начинает заново: оборванный `.part` удаляется перед
каждой попыткой. Для файла в 1.5 ГБ на нестабильной мобильной сети это
раздражает — но гарантирует отсутствие «половина от старой попытки + половина
от новой».

### API-ключ хранится открытым текстом

`deepseek_key` лежит в таблице `settings` обычной SQLite рядом с остальными
данными. Шифрования (Android Keystore, EncryptedSharedPreferences) нет.
Для устройства без root этого умеренный риск, но при утере приложения или
бэкапе ключ уязвим.

### Только один диалог

Ни нескольких чатов, ни переименования, ни экспорта. Вся история — одна таблица,
`clearChat()` удаляет её целиком.

## Грабли, на которые уже наступили

Эти ловушки уже исправлены, но знание о них экономит время:

| Проблема | Причина | Решение в коде |
|---|---|---|
| Штатный чат-шаблон Qwen падает на системном сообщении | шаблон делает `'<|im_start|>system\n' + messages[0].content`, а LiteRT передаёт `content` списком блоков | собственный `CHATML_TEMPLATE`, берёт `block.text` |
| Парсер шаблона не понимает `{%-` / `-%}` / `{{-` / `-}}` | урезанный движковый парсер | в шаблоне нет whitespace-control |
| `\n` внутри строковых литералов шаблона не парсятся | тот же парсер | только escape-последовательности |
| GPU-движок падает только на первой генерации | ленивая инициализация OpenCL | пробная микрогенерация при загрузке (`probe = true`) и откат на CPU |
| Koog: `No KoogHttpClient.Factory provider found` | `META-INF/services` вырезается при упаковке APK | фабрика передаётся явно, движок CIO указан явно |
| `UnsatisfiedLinkError` роняет приложение | это `Error`, а не `Exception`; `catch (Exception)` его не ловит | `rethrowIfFatal` + `catch (Throwable)` в критичных местах |
| Запрос вне темы базы получает мусорные чанки и вынужденный отказ | не было порога схожести | `MIN_SCORE` и проверка пересечения корней |
| На «привет» модель отвечает «в документах этого нет» | слишком жёсткий RAG-промпт | `QueryRouter` + свободный ответ при пустом контексте |
| Индикатор загрузки одной модели горит на карточке другой | глобальный статус не различал модели | прогресс ведётся по `model.id`, статус — только для выбранной |
| Два параллельных скачивания в один `.part` | флаг ставился асинхронно, второй тап успевал раньше | синхронная отметка в карте `downloading` до `scope.launch` |
| После удаления файла UI зависал на несуществующей модели | выбор не снимался | `deleteLlm` / `deleteEmbed` сбрасывают выбор (тест `DeleteDeselectTest`) |
| Смена embedding-модели ломала индекс | векторы разной размерности сравнивались | `clearChunks()` + фильтр `dim == embBridge.dim` |
| Русский текст обрезался в эмбеддингах | `maxInputLength = 512` токенов ≈ 1000 символов | `maxChars = 1000` в чанкере |
| Гигабайтная модель обрывалась по таймауту | общий `requestTimeoutMillis = 120 с` | 7 суток на запрос скачивания |
| Модель на HTTP 404 повторялась три раза | `IllegalStateException` попадал в общий retry | HTTP-ошибки пробрасываются сразу |
| Отмена превращалась в «Ошибка» | `catch (Exception)` ловил `CancellationException` | явный переброс `CancellationException` |

## Точки роста

**Ближайшие**

1. Покрыть тестами `StructureChunker` и `EmbedMath` (особенно little-endian конвертацию).
2. Решить судьбу мёртвого кода `task2.db/presentation/ui/di`.
3. Пересмотреть ProGuard-правила под LiteRT-LM и включить подпись релизов.
4. Заменить `combine` из 13 потоков на типизированное состояние.
5. Починить `llmStatus !is EngineStatus.Error || true`.

**Среднесрочные**

6. `DocumentLoader`-интерфейс: PDF, текстовые файлы, произвольные URL.
7. ANN-индекс при росте корпуса + калибровка `MIN_SCORE` по выборке.
8. Шифрование API-ключа (Keystore на Android).
9. Несколько диалогов с историей.
10. Реальный `EmbeddingEngine` для JVM, чтобы десктоп стал пригоден для оценки RAG.

**Долгосрочные**

11. LLM-извлечение фактов вместо регулярок (поле `FactEntity.source` и миграция
    v1→v2 уже под это заложены).
12. Гибридный поиск (BM25 + dense) вместо текущей проверки пересечения корней.
13. Reranking топ-хитов перед формированием контекста.
14. Кэш ответов, чтобы повторные вопросы не дёргали модель.

## Полезно знать при отладке

* Модель можно подложить вручную: положить `.litertlm` в `models/llm/` или
  `models/embed/` под именем из `ModelCatalog` / `EmbedCatalog` — приложение
  увидит файл при следующем запуске.
* `lastMaxScore` (максимальный косинус последнего запроса) выведен в `Task3UiState`
  как `lastScore` — удобный индикатор для настройки `MIN_SCORE`.
* Если GPU-бэкенд не работает на конкретном устройстве, приложение не сломается:
  откат на CPU происходит внутри `tryOpen`.
* Сообщение `Модель не скачана — скачай её в Настройках` означает, что путь
  в `modelsDir` отсутствует или файл пустой (`length() == 0`).
* `Не загрузилась в LiteRT: …` — файл на месте, но рантайм его не открыл:
  скорее всего повреждён или несовместимая версия бандла.
